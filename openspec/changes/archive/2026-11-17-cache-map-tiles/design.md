# Design

## Context

`maps.py` の `fetch_mosaic` は、ビューポートに必要なタイルを毎回 HTTP で取り、Pillow で結合する。HTTP クライアントは `httpx.Client` を都度作り、キャッシュ層はない。天気には `weather.json` の前回値キャッシュがあるが、地図タイルにはない。

OSM のタイル応答は `Cache-Control: max-age=...`（実測で約 16,000 秒）、`ETag`、`stale-while-revalidate=604800`、`stale-if-error=604800` を返す。OSMF のタイル利用ポリシーは、キャッシュを must とし、期限切れには条件付きリクエストを求めている。現状は同じ地点の地図を毎朝 25 枚前後取り直しており、この点でポリシーに沿っていない。

制約は、単一 venv、鍵なし、無人 cron、依存追加なし、地図取得の失敗時は画像を省くこと。設定・CLI・PDF の契約は変えない。

## Goals / Non-Goals

**Goals:**

- タイルをローカルに保存し、HTTP の鮮度指示に従って再利用する。
- 期限切れは条件付きリクエストで再検証し、本文の再ダウンロードを避ける。
- キャッシュの不具合で地図の生成を止めない。
- キャッシュのファイル名から地図の座標やタイル URL を推測できないようにする。

**Non-Goals:**

- オフライン地図、先読み、期限切れタイルのネットワーク失敗時の代用。
- キャッシュの定期削除・容量上限・管理コマンド。
- 経路・天気・写真のキャッシュ。
- タイル提供元の切り替え、設定キーの追加。
- 7日固定 TTL への単純化（HTTP ヘッダを無視するため）。

## Decisions

### 1. `max-age` と `ETag` に従い、7日固定 TTL にはしない

タイル応答の `Cache-Control: max-age` を鮮度として保存し、期限切れは `If-None-Match` で再検証する。OSM の max-age は約4.5時間なので、毎朝の実行ではほぼ毎回 304 になるが、本文は転送されない。7日固定 TTL は実装が単純だが、サーバが指定した鮮度を無視して最大7日古い地図を刷ることになり、ポリシーの「HTTP キャッシュ指示に従う」に反する。7日は `max-age` が無い場合のフォールバックにだけ使う。

`stale-while-revalidate` を使った「古いタイルを即返して裏で再検証」は、単発 CLI では裏側の実行主体がないため採用しない。`stale-if-error` による期限切れタイルの代用も、既存の「取れなければ地図なし」という縮退とポリシーのオフライン利用の扱いを変えるため、この変更では行わない。

### 2. キャッシュは「タイルのバイト列＋メタデータ」の2ファイル

`cache_dir()/tiles/<sha256(url)>.tile` にバイト列、`<sha256(url)>.json` に `{"etag": ..., "expires_at": ...}` を置く。URL をそのままファイル名にすると、鍵付きタイル URL を使った場合に鍵や座標がディレクトリに残る。ハッシュにすれば、URL も座標も保存しない。

書き込みは同じディレクトリの一時ファイルに書いて `os.replace` する。バイト列を先、メタデータを後に書く。途中で落ちた場合はメタデータが古いか無い状態になり、次回はキャッシュミスまたは再検証になる。逆順にすると「新しいメタデータ＋古いバイト列」で 304 を返してしまう危険があるため、この順序を守る。

単一 JSON に base64 で詰める案は、33% の容量増とデコードの手間があり、バイト列をそのまま扱えない。SQLite はこの規模には重い。2ファイル方式を採る。

### 3. 鮮度の判定

`expires_at = 取得時刻 + max_age`。`max_age` は `Cache-Control` の `max-age` を読み、無ければ7日。`no-store` が付いていれば保存しない。`now < expires_at` の間だけ、ネットワークなしでキャッシュを使う。

304 の応答にも `Cache-Control` が付く場合はその `max-age` で `expires_at` を更新する。付かない場合は7日で更新する。ETag が無いタイルは、期限切れ後に条件付きリクエストをせず通常の GET にする。

### 4. 取得の流れ

タイルごとに次を行う。

1. キャッシュを読む。読めない・壊れている・メタデータが不正ならミスとして扱う。
2. 新鮮なら、そのバイト列を画像として開く。開けなければミスとして扱う。
3. 期限切れなら、ETag があれば `If-None-Match` を付けて GET する。
4. 304 なら保存済みのバイト列を使い、鮮度を更新する。
5. 200 なら画像として開く。開けたらバイト列と ETag を保存し、その画像を使う。開けなければ従来通り `OSError` として扱い、壊れたタイルは保存しない。
6. 304 なのに保存済みのバイト列が無い場合は、条件を外して取り直す。

タイルの取得失敗（HTTP エラー、タイムアウト）は従来通り `RuntimeFailure` にし、`build_map_page` が警告して画像を省く。キャッシュの読み書きの失敗は握りつぶし、ネットワーク取得に進む。

### 5. キャッシュは best-effort、失敗は静かに縮退する

キャッシュのディレクトリが作れない、書けない、読めない場合でも、地図の生成は止めない。キャッシュは最適化であり、正しさの前提ではない。警告は出さない（毎朝の cron の標準エラーを騒がせないため）。`doctor` にも追加しない。

破損したキャッシュを検出した場合は、そのタイルだけ取り直す。全タイルを捨てる必要はない。

### 6. テストはキャッシュディレクトリを隔離し、時計を固定する

`XDG_CACHE_HOME` を `tmp_path` に向けて、実ユーザのキャッシュを汚さない。`respx` でタイル応答をモックし、リクエスト回数と `If-None-Match` を検証する。鮮度は `expires_at` を過去にしたメタデータを書くか、`time.time` を monkeypatch して作る。

書き込み失敗は、読み取り専用ディレクトリの chmod ではなく、書き込み関数を monkeypatch して `OSError` を出させる（root 実行でも再現できる）。壊れたキャッシュは、`.tile` に画像でないバイト列を置いて検証する。304 の応答は `httpx.Response(304)` で返す。

## Risks / Trade-offs

- **毎回 25 枚の条件付きリクエストが発生する** → 304 は本文が無く、負荷は小さい。ポリシーが求める再検証の範囲。
- **ETag を返さない提供元** → 期限切れ後は通常 GET になる。動作はするが転送量は減らない。
- **期限切れファイルが残り続ける** → 1回あたり数十枚、数百 KB 程度。削除は非目標。必要になったら別 change で容量上限を入れる。
- **同時実行で二重取得する** → 原子的な replace で壊れない。重複取得は許容する。
- **鍵付きタイル URL のキャッシュ** → ファイル名はハッシュで、URL も鍵も保存しない。鍵を変えるとキャッシュミスになるが、古いファイルは残るだけ。
- **時計のずれ** → 鮮度が早め/遅めに切れる。地図の正しさには影響しない。
- **壊れた画像をキャッシュしてしまう** → 画像として開けたものだけ保存する。開けないバイト列は保存しない。
- **他の地図変更との衝突** → `maps.py` の取得部分と描画部分は独立している。`tests/test_maps.py` を共有するため、適用順に応じてフィクスチャとキャッシュ隔離を統合する。

## Migration Plan

保存形式の移行はない。次回実行からキャッシュが作られる。ロールバックは `tilecache.py` と `fetch_mosaic` の変更を戻し、キャッシュディレクトリを削除するだけ。設定・CLI・PDF の互換性に影響はない。

`polish-map-page` とは独立して適用できる。両方を適用する場合、`fetch_mosaic`（取得）と描画処理（`draw_route` / A/B）は別の関数なので、競合はテストの共通部分に限られる。
